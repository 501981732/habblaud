# 四种 Agent 的本机接入与排错

返回 [中文首页](../../README.md) · [服务器说明](../../server/README.md) · [DSH 插件](../../integrations/dsh/README.md) · [Pi 扩展](../../integrations/pi/README.md)

这里的“来源”指 Claude Code、Codex、DeepSeek Harness（DSH）、Pi；“模型”指这些来源内部使用的 GLM、Claude、GPT 等。请先让原来的运行环境正常工作，再启动 Habblaud。Habblaud 不代替模型登录、认证或项目配置。

## 先确认服务

```bash
node --version
npm ci
npm run build
npm start
```

Node.js 至少 22.12。默认打开 <http://127.0.0.1:4747>。`GET /api/health` 可用于确认服务器可用及各来源启用状态；`GET /api/snapshot` 会显示办公室当前已识别的 Agent。没有会话时办公室为空是正常情况，可用 `npm run demo` 看虚构角色。

网页消息、完整终端、历史和审批只在**本机回环绑定**时开启。若设了 `HABBLAUD_HOST=0.0.0.0` 或 Docker `HABBLAUD_BIND=0.0.0.0`，这些操作主动关闭，避免把对话与写操作暴露给局域网。

## Claude Code

1. 打开一个本机 Claude Code 会话并发送至少一条消息，确保它写出了会话记录。
2. Habblaud 自动发现 `~/.claude*` 或 `CLAUDE_CONFIG_DIR`；另一个目录用 `HABBLAUD_CLAUDE_DIRS`（逗号分隔）。
3. 要从网页收发消息、处理许可和看实时用量，运行 `npm run mod:install`。检查用 `npm run mod:status`。
4. 对于已打开的 Claude Code 会话，执行 `/reload-plugins` 或重开会话。
5. 不需要网页消息时，用 `npm run mod:install -- --sem-mensagens` 或停用服务端 `HABBLAUD_MENSAGENS=0`。

旧版 Claude Code 可用 `npm run usage:install` 与 `npm run hooks:install`，但这些是旧接法；具体备份/移除行为见 [插件说明](../../mod/README.md)。

## Codex

1. 打开本机 Codex CLI 或 Desktop 会话并发送一条消息。刚打开却没有会话记录时，Habblaud 还不知道其项目目录。
2. Habblaud 自动发现 `CODEX_HOME`、`~/.codex*`；其他目录用 `HABBLAUD_CODEX_DIRS`（逗号分隔）。
3. 运行 `npm run codex:install`，在 Codex 的 `/hooks` 批准，然后重开相关会话；`npm run codex:status` 可检查安装。
4. 网页消息通过 `codex queue`。`codex` 未进入 `PATH` 时设 `HABBLAUD_CODEX_BIN=/绝对路径/codex`。
5. 如果 Habblaud 运行于 Docker，宿主机另运行 `npm run codex:bridge`，让容器的消息能交给宿主 Codex。

Codex 的模型名称按原会话显示。Habblaud 不读取 Codex 的 `auth.json`、`config.toml` 或 shell 快照。

## DeepSeek Harness 与 GLM

1. DSH 中先确认 GLM 自己能正常会话。Habblaud 不修改 DSH 模型或认证。
2. 启动 Habblaud Node 服务，让它生成私有 `bridge.json`。
3. 在仓库目录运行 `npm run dsh:install -- --profile web`；检查 `npm run dsh:status -- --profile web`。若 DSH CLI 不在 `PATH`，加 `--dsh /绝对路径/dsh`。
4. 在目标 DSH profile 中打开/新建一个会话。Habblaud 应把它标成 `DSH`，模型另显示为 DSH 报告的 GLM 版本。
5. 若插件清单已安装但办公室没出现会话，检查 DSH 进程是否热重载；必要时按 DSH 官方方式重新启动对应 profile。确认两端使用**同一个** `HABBLAUD_BRIDGE_CONFIG` 路径。
6. 通过原生插件才能读取 DSH 已解码的压缩历史；直接看磁盘上的 `.zstd` 文件不能验证 Habblaud 历史路径。

消息成功投递的意思是 DSH 接受了请求，模型处理仍需看会话后续事件。审批仅在有本地网页且桥在线时临时接管；失败则回 DSH 原 Web UI。若碰到“同名 bundle 来源不同”或已禁用，安装器会停下并保留配置，先按 DSH profile 的现有安装状态排查。

## Pi

1. 构建后，在 Pi 进程命令行加入 `--extension /绝对路径/habblaud/integrations/pi/dist/index.js`。
2. Pi 实时会话来自正在运行的 extension。若只有旧 session JSONL，历史可显示，但不会凭历史把 Agent 标成在线。
3. 默认扫描 `~/.pi/agent/sessions/`，或 `PI_CODING_AGENT_DIR/sessions/`。多个 agent 目录用 `HABBLAUD_PI_DIRS`；分隔符是当前平台的 Node `path.delimiter`。
4. 若需在 Habblaud 中处理 Pi 工具审批，启动 Pi 前设 `HABBLAUD_PI_APPROVALS=1`。开启后每次工具调用均需审批；无可用页面会回 Pi 确认界面，无交互界面或超时会拒绝。
5. 检查 Pi 历史时请切换过分支：终端应只显示当前叶节点的祖先链，不应把被放弃的分支混进来。

Pi 扩展加载与模型真实调用是两件事。运行时联调结论在本次 PR 验收记录单独说明；没有真实模型请求的测试只证明 SDK、事件和桥链路。

## 配置位置和隐私

`HABBLAUD_DATA_DIR` 默认是 `~/.habblaud`。服务器生成的 `bridge.json` 含本机访问令牌，文件权限应为私有；DSH/Pi 插件未设变量时也读 `~/.habblaud/bridge.json`。若服务器用了临时数据目录，先给服务器与插件进程指定相同的 `HABBLAUD_BRIDGE_CONFIG=/绝对路径/bridge.json`，再启动它们。不要输出令牌内容，也不要把真实业务对话、账户目录或个人路径放进公开 PR。

Habblaud 的中文化只作用于产品文案：语言开关切换导航、活动、状态、日期/数字格式；用户消息、工具参数、命令、路径和模型名保持原文。若看到某段没有翻译，先判断它是来自模型的原始内容，还是 Habblaud 自己生成的 UI 文案。
